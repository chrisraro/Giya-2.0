# 41 — PWA & Offline

How the consumer PWA (`33-consumer-pwa.md`) installs, caches, queues, syncs, and pushes. Stack: **next-pwa (Workbox under the hood) + Service Workers**, Locked per `../10-architecture/11-tech-stack.md` with two non-negotiable rules restated here because this module implements them: **the SW never caches API responses containing another user's data**, and **caches are versioned and purged on deploy and on logout**. Phasing per `../00-product/02-roadmap.md`: MVP = app-shell caching + installability + push; V1 = offline receipt queue, offline wallet viewing, installability polish; SCALE = periodic background sync.

The business and admin portals (`app/(business)`, `app/(admin)`) are **excluded from SW scope** — staff/admin surfaces must never serve stale tenant data; the SW registration is scoped to consumer routes only.

## 1. Service worker architecture

One SW, generated by next-pwa at build time, registered from the consumer layout. Cache names are versioned with the build id: `giya-{cacheClass}-{buildId}` (see §7 Update flow).

### Precache [MVP]

Workbox precache manifest: app shell (framework chunks, consumer route shells, global CSS, fonts, icon set, manifest) + the offline fallback document `/offline` (route inventory in `33-consumer-pwa.md`). Precache is content-hashed; unchanged assets survive deploys without refetch.

### Runtime caching strategies (registry — one Workbox route per row)

| Asset class | Match | Strategy | Cache config |
|---|---|---|---|
| Documents (navigations) | consumer route navigations | **NetworkFirst**, 3s timeout | fallback → cached page, else precached `/offline` |
| Static assets | `/_next/static/*`, fonts | **StaleWhileRevalidate** | 30d expiry (content-hashed anyway) |
| Images | `next/image` output + public buckets (`products`, `promotions`, `rewards`, `menus`, `avatars`, `announcements` per `../10-architecture/11-tech-stack.md`) | **CacheFirst** | LRU `maxEntries: 200`, `maxAgeSeconds: 7d`, `purgeOnQuotaError: true` |
| Signed-URL media (`receipts`, `business-documents`) | private buckets | **NetworkOnly** | never cached: URLs are 5-min signed, content is sensitive (`../10-architecture/15-security.md`) |
| Public API GETs | `/api/v1/businesses*`, CMS/banners | **NetworkFirst** | maxAge 10min, maxEntries 50 — mirrors the `s-maxage=60, stale-while-revalidate=300` server policy (`../10-architecture/13-api-standards.md`) |
| **Own-user wallet API GETs** [V1] | `/api/v1/me/points*`, `/me/rewards*`, `/me/loyalty-cards`, `/me/receipts*`, `/me/notifications*` | **NetworkFirst**, short-lived | maxAge 24h, powers §4 offline viewing |
| All other API | `/api/v1/*` incl. `/api/v1/ai/*`, POSTs | **NetworkOnly** | POSTs are never cached; failed receipt POSTs go to the §3 outbox instead |

### Security rules for the `me`-cache (the only cached authenticated data)

- Server marks these responses `Cache-Control: private` (per `../10-architecture/13-api-standards.md` authenticated-GET rule; these endpoints are the documented opt-in). The SW cache is the only cache layer; no shared/CDN caching.
- Cache entries are keyed inside a per-user cache name: `giya-me-{buildId}-{userId-hash}` (hash of the Supabase user id, obtained via `postMessage` from the app at login). A response is only ever written to the cache of the session that fetched it — another user logging in on the same device gets a fresh, empty cache. **Never cache another user's data** is thereby structural, not conventional.
- **Purged on logout:** the logout action `postMessage({type:'PURGE_USER_CACHES'})` → SW deletes all `giya-me-*` caches and the §4 IndexedDB snapshot before the session is destroyed. Purged on deploy via buildId rotation (§7). Sensitive amounts are data, not secrets, but treat the device as shared by default.

### Workbox route config sketch (`next.config.ts` → next-pwa `runtimeCaching`)

```ts
// Order matters: first match wins. buildId injected at build time.
runtimeCaching: [
  { urlPattern: ({request}) => request.mode === 'navigate',
    handler: 'NetworkFirst',
    options: { cacheName: `giya-pages-${buildId}`, networkTimeoutSeconds: 3,
               precacheFallback: { fallbackURL: '/offline' } } },
  { urlPattern: /\/_next\/static\/.*/,
    handler: 'StaleWhileRevalidate',
    options: { cacheName: `giya-static-${buildId}` } },
  { urlPattern: ({url, request}) => request.destination === 'image' && isPublicBucket(url),
    handler: 'CacheFirst',
    options: { cacheName: `giya-images-${buildId}`,
               expiration: { maxEntries: 200, maxAgeSeconds: 604800, purgeOnQuotaError: true } } },
  { urlPattern: /\/api\/v1\/(businesses|cms|banners)/,
    handler: 'NetworkFirst',
    options: { cacheName: `giya-public-api-${buildId}`,
               expiration: { maxEntries: 50, maxAgeSeconds: 600 } } },
  { urlPattern: /\/api\/v1\/me\/(points|rewards|loyalty-cards|receipts|notifications)/,
    handler: 'NetworkFirst',   // [V1] — cacheName suffixed per-user at runtime, see §1 security rules
    options: { cacheName: `giya-me-${buildId}`, expiration: { maxAgeSeconds: 86400 } } },
  // everything else /api/v1/* : NetworkOnly (default — no route registered)
]
```

Signed-URL media (`receipts`, `business-documents` hosts) must be excluded from the image route matcher (`isPublicBucket`) — enforced by a unit test on the matcher, not by convention.

### SW ⇄ app message protocol (registry — `src/lib/pwa/messages.ts`)

All `postMessage` payloads are typed `{type, payload?}`; unknown types are ignored (forward-compatible).

| Type | Direction | When | Effect |
|---|---|---|---|
| `SET_USER` | app → SW | login / session restore | SW derives the per-user me-cache name (§1) |
| `PURGE_USER_CACHES` | app → SW | logout, account deletion | delete `giya-me-*` caches; app separately clears IndexedDB |
| `SKIP_WAITING` | app → SW | user confirms update toast | `skipWaiting()` (§7) |
| `OUTBOX_CHANGED` | SW → app | after sync-handler replay | app invalidates `['receipts','list']` and refreshes queue UI (§3) |
| `NAVIGATE` | SW → app | `notificationclick` with focused client | client-side route to `data.route` (§5) |

- Capture `beforeinstallprompt`, `preventDefault()`, stash the event in `uiStore` (`33-consumer-pwa.md`). **Never prompt cold.**

## 3. Offline receipt queue [V1]

Capture must work in a basement milk-tea shop. The scanner (`33-consumer-pwa.md`) runs fully client-side through capture → crop → compress; only upload+submit need the network. When offline (or submit fails with a network error), the submission lands in an **IndexedDB outbox** instead of erroring.

### Outbox schema (IndexedDB, db `giya-offline` v1, store `receipt_outbox`)

| Field | Type | Notes |
|---|---|---|
| `id` | string (UUID) | outbox key |
| `image` | Blob | compressed JPEG (≤1.5MB, compression contract in `33-consumer-pwa.md`) |
| `client_sha256` | string | computed at capture; outbox dedupe key + advisory server pre-check (authoritative hash is server-computed, `36-receipt-ocr-pipeline.md`) |
| `business_id` | string \| null | pre-bound scans; null for generic [V1] |
| `captured_at` | ISO string | shown in queue UI; sent for context |
| `idempotency_key` | string (UUID) | minted at capture, reused on every replay attempt |
| `attempts` | number | replay bookkeeping |
| `last_error` | string \| null | last failure class |
| `status` | `'queued' \| 'uploading' \| 'failed'` | drives UI |

### Replay

1. Registration: on enqueue, `registration.sync.register('receipt-outbox')` (Background Sync API). Fallback (iOS/unsupported, §6): replay attempts on app launch and on the `online` event.
2. The sync handler drains the outbox FIFO: presign → PUT image → `POST /api/v1/receipts` with the stored `Idempotency-Key` and `client_sha256`.
3. **Retry/backoff:** per item, exponential 30s → 2m → 10m → 1h, max 5 attempts (aligned with worker retry norms, `39-background-jobs.md`), then `status='failed'` with a manual "Retry" button. 4xx domain errors (e.g. `RECEIPT_DUPLICATE`) are terminal immediately — no retry.
4. **Replays are safe by construction (server dedupe):** the `Idempotency-Key` replays the stored response (`../10-architecture/13-api-standards.md`) — this is the primary replay guard, since the authoritative `receipts.sha256` is computed server-side over canonical re-encoded bytes and is DB-unique (`../20-data/24-schema-receipts-ai.md`) — a double-submitted image can never award twice (also guarded by the one-earn-per-receipt ledger index, `../20-data/23-schema-campaigns.md`). A `RECEIPT_DUPLICATE` on replay is treated as success-already-processed and the item is removed with an informational toast.
5. On success: delete outbox row, notify the user ("Receipt uploaded — processing"), and the normal Realtime status flow takes over next time the screen opens.

### Drain algorithm (sync handler, `src/lib/pwa/outbox.ts`)

```ts
async function drainOutbox() {
  const items = await outbox.getAll({ status: ['queued', 'failed'] }); // FIFO by captured_at
  for (const item of items) {
    if (!due(item)) continue;                       // backoff schedule below
    await outbox.update(item.id, { status: 'uploading' });
    try {
      const { url, image_path } = await presign();  // POST /api/v1/receipts/uploads
      await putToStorage(url, item.image);
      await postReceipt({ image_path, client_sha256: item.client_sha256, business_id: item.business_id },
                        { idempotencyKey: item.idempotency_key });
      await outbox.delete(item.id);                 // success (incl. Idempotent-Replayed: true)
      notifyClient('OUTBOX_CHANGED');
    } catch (e) {
      if (isDomainError(e)) {                       // 4xx: RECEIPT_DUPLICATE, VALIDATION_FAILED…
        await outbox.delete(item.id);               // terminal; duplicate = already processed
        recordTerminal(item, e);
      } else {                                      // network/5xx/RATE_LIMITED
        const attempts = item.attempts + 1;
        await outbox.update(item.id, attempts >= 5
          ? { status: 'failed', attempts, last_error: classify(e) }   // manual retry only
          : { status: 'queued', attempts, last_error: classify(e) }); // backoff: 30s,2m,10m,1h
      }
    }
  }
}
```

`RATE_LIMITED` honors `Retry-After` before the next item — the whole drain pauses, preserving FIFO.

### User-visible queue state

- `/scan` and `/receipts` show a persistent "N receipts waiting to upload" card with per-item thumbnail, `captured_at`, status, and manual retry/delete. Offline submit confirmation says exactly what happened: "Saved on your phone — we'll send it when you're back online."

### Caps & quota

- **Max 10 queued receipts.** The 11th capture is blocked with "Upload your pending receipts first." (~15MB worst case — safely inside mobile quotas and a natural fraud-velocity bound consistent with the 60/day rate limit.)
- On `QuotaExceededError` during enqueue: attempt image-cache cleanup (Workbox LRU purge), retry once, else tell the user storage is full. See §8.

## 4. Offline wallet & rewards viewing [V1]

Read-only last-synced snapshot so a consumer can show a counter their claimed reward *list* or check balances with no signal.

- **Source:** the §1 own-user NetworkFirst API cache serves stale GETs automatically. Additionally, a structured snapshot is written to IndexedDB store `wallet_snapshot` after each successful wallet/rewards/cards fetch: `{synced_at, points: [business_customers projection], claims: [reward_claims projection], cards: [loyalty_cards+loyalty_programs projection]}` — used by TanStack Query as `initialData` hydration when offline, keyed per user (purged on logout, §1).
- **Staleness banner:** whenever data is served without a network confirm, show "Offline — last updated {relative time from synced_at}" on `/wallet`, `/rewards`, `/cards`.
- **Disabled offline** (buttons rendered disabled with explanation, not hidden): reward claiming (server-atomic points/inventory transaction), review posting, favorites toggle, AI chat (`33-consumer-pwa.md`), profile edits.
- **NO offline redemption — deliberate security decision.** The redemption QR is an ephemeral server-signed single-use token (JWT, `jti` in Redis, TTL 5 min, `../10-architecture/15-security.md`); minting it client-side or pre-minting long-lived tokens would reopen the replay/screenshot fraud the design exists to kill (threat #1 in the threat model). Offline, `/rewards/claims/[claimId]` shows the claim details plus: "You need a connection for a few seconds to generate your redemption code — it keeps your rewards safe from copies." Any offline redemption path (staff-side deferred validation) is a [SCALE] design exercise, not a v1 gap.

## 5. Push notifications (FCM web push)

All sends go through the notification service + queue (`30-platform-core.md`, `39-background-jobs.md`); this section is the client lifecycle. Integration config in `42-integrations.md`.

- **Permission priming [MVP]:** value-first sheet after first approved receipt (strategy + cooldowns in `33-consumer-pwa.md`). Only after the user accepts the sheet do we call `Notification.requestPermission()` — a browser-level "Block" is near-irreversible.
- **Token registration:** on grant, `getToken()` (FCM SDK, VAPID key) → `POST /api/v1/me/devices {fcm_token, platform:'web', user_agent}` → upsert `user_devices` (`fcm_token` is unique; re-registration on the same device updates `last_seen_at`).
- **Rotation/cleanup:** re-validate token on every app open (`onTokenRefresh`/`getToken` returns rotated tokens) and re-POST when changed; server revokes the old row. FCM `UNREGISTERED` errors on send mark `user_devices.is_revoked=true`; devices with `last_seen_at` > 180 days are pruned by the cleanup queue (`../20-data/21-schema-identity.md`). User-visible list/revoke UI is `/profile/devices` [V1].
- **Foreground vs background:** background pushes are displayed by the SW `push` handler (title/body/icon + `data.route`). Foreground (`onMessage`) never shows a system notification — it shows an in-app toast and invalidates `['notifications','unread-count']`. Every push has an `in_app` `notifications` sibling row, so nothing exists only as a push.
- **Click → deep link:** SW `notificationclick` → focus an existing client and `postMessage` the route, else `clients.openWindow(route)`. Routes come from `notifications.data` (`{route, params}`) — kind→route table in `33-consumer-pwa.md`. Delivery receipt: opening from a push marks the sibling row `read_at` via the standard mark-read call.

### SW push handlers (sketch)

```ts
self.addEventListener('push', (event) => {
  const { title, body, icon, data } = event.data.json();   // {data: {route, params, notification_id}}
  event.waitUntil(self.registration.showNotification(title, { body, icon, data }));
});
self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  const route = event.notification.data?.route ?? '/notifications';
  event.waitUntil(clients.matchAll({ type: 'window' }).then((wins) => {
    const win = wins.find((w) => w.url.startsWith(self.location.origin));
    return win ? (win.focus(), win.postMessage({ type: 'NAVIGATE', payload: { route } }))
               : clients.openWindow(route);
  }));
});
```

## 7. Update flow

1. CI injects the build id (git SHA) into the SW (`__BUILD_ID__`); every cache name embeds it (§1).
2. New deploy → browser fetches changed SW → installs in parallel, enters `waiting` (no `skipWaiting` by default — never yank an in-progress scan).
3. App detects `registration.waiting` → non-blocking toast: "A new version of Giya is ready — Refresh". Confirm → `postMessage({type:'SKIP_WAITING'})` → SW `skipWaiting()` → `controllerchange` → `location.reload()`.
4. **Auto-activate exception:** if the waiting SW is detected during app launch (before first interaction), activate immediately — no toast needed.
5. On `activate`, the new SW deletes every cache whose name lacks the current build id (this is the "purged on deploy" guarantee from `../10-architecture/11-tech-stack.md`). Precache diffing keeps unchanged assets.
6. A stale client calling a removed API shape is prevented by additive-only `v1` changes (`../10-architecture/13-api-standards.md`); a forced-upgrade envelope hook is reserved for emergencies via `feature_flags`.

## 8. Storage management

- **Budget:** precache ~3–5MB · image cache ≤ ~40MB (LRU 200 entries) · me-cache ≤ ~2MB · outbox ≤ ~15MB (10 items) · wallet snapshot ≤ ~200KB.
- **Persistence:** after the first item enters the outbox, request `navigator.storage.persist()` (best-effort; Chromium usually grants for installed PWAs). Check `navigator.storage.estimate()` before enqueue; warn at >80% usage.
- **Eviction handling:** all Workbox caches set `purgeOnQuotaError: true` so images are sacrificed first. **Safe to lose:** every cache and the wallet snapshot (rebuilt from Postgres — mirrors the Redis rule in `../10-architecture/11-tech-stack.md`). **Not safe to lose:** the receipt outbox — hence `persist()`, the 10-item cap, and the visible queue nudging prompt upload. If eviction still claims the outbox (iOS 7-day rule), the receipt is gone and we never pretend otherwise: no phantom "pending" state survives without its IndexedDB row.
- Logout purge order: outbox check (warn if non-empty: "You have 2 unsent receipts — they'll be deleted"), then IndexedDB stores, then `giya-me-*` caches, then session.

## 9. Offline UX conventions & the fallback page

- **Connectivity signal:** a single `useOnlineStatus()` hook (listens to `online`/`offline` + a lightweight `HEAD /api/v1/health` heartbeat on focus, because `navigator.onLine` lies on captive portals). Drives one global, non-blocking "Offline" pill in the app bar — individual screens never invent their own banners except the staleness banner (§4) and the outbox card (§3).
- **`/offline` fallback page** (precached, zero external deps, inline styles): Giya mark, "You're offline" in the user's locale, and live links to the routes that *do* work from cache — `/wallet`, `/rewards`, `/cards`, `/receipts` — plus the outbox count if any. It is a navigation fallback only; API failures inside a loaded app render inline error states (`33-consumer-pwa.md` state matrix), never a full-page takeover.
- **Never fake success:** offline actions either queue with explicit "saved on your phone" language (receipts) or refuse with an explanation (claims, redemption, reviews). No optimistic UI for anything that moves points or inventory.
- **Time skew:** countdowns (redemption token 5-min TTL) always trust server-issued `exp`, rendered against `Date.now()`; if skew > 30s is detected from response `Date` headers, show "code expires shortly" instead of a precise countdown.

## 10. Observability

- **Sentry** (per `../10-architecture/11-tech-stack.md`): SW errors captured via the SW Sentry integration; offline events are buffered by Sentry's offline transport (IndexedDB) and flushed on reconnect — capped at 30 events, drop-oldest.
- **Metrics** (client → analytics collection per `40-analytics.md`): `outbox_enqueued`, `outbox_replayed{attempts}`, `outbox_failed_terminal{error_class}`, `outbox_dropped_quota`, `sw_update_{shown,accepted}`, `push_token_{registered,rotated,revoked}`, `offline_session_started` (app opened with no network). Dashboards alert on replay success rate < 95% over 24h and on outbox terminal-failure spikes (`../50-ops/52-monitoring-observability.md`).
- **IndexedDB versioning:** db `giya-offline` uses integer schema versions with `onupgradeneeded` migrations kept in `src/lib/pwa/db.ts`; a failed migration drops and recreates *snapshot* stores (safe to lose) but never the `receipt_outbox` store — if the outbox itself cannot migrate, surface a blocking "update the app to send pending receipts" state rather than silently discarding.

## 11. Testing (per `../50-ops/51-testing-strategy.md` conventions)

Playwright E2E, project `pwa-offline`, using `context.setOffline(true)` / CDP network conditions; SW enabled in the test browser profile. Scenarios:

1. **Offline navigation:** visit `/` online → go offline → navigate to cached business page (renders stale) and an uncached route (renders `/offline` fallback).
2. **Outbox happy path:** offline → capture+crop+compress → submit → outbox row visible with queue card → go online → auto-replay → assert exactly one `receipts` row, outbox empty, toast shown.
3. **Replay idempotency:** kill the connection mid-replay after the POST is sent → reconnect → second replay with same `Idempotency-Key`/`client_sha256` → assert still exactly one `receipts` row and one `earn` ledger row.
4. **Outbox cap:** enqueue 10 → 11th capture blocked with the cap message.
5. **Offline wallet:** load wallet online → offline → balances/claims/cards render from snapshot with staleness banner; claim button disabled with explanation.
6. **No offline redemption:** offline → open `/rewards/claims/[claimId]` → assert no QR rendered, explanation copy present; online → token mints, QR renders, expires at 5:00.
7. **User-cache isolation:** login as A, load wallet, logout, login as B offline → assert zero A data served (empty states, not A's balances).
8. **Update flow:** deploy new build id in test harness → toast appears → confirm → new SW controls, old-build caches deleted.
9. **Push deep link:** simulated `push` event → notification shown; `notificationclick` → app focused on `data.route`.
10. **Quota pressure:** fill image cache, trigger `QuotaExceededError` on enqueue → LRU purge path runs, receipt still enqueues.

## Decision log (why, in one line each)

| Decision | Rationale |
|---|---|
| NetworkFirst for documents, not app-shell SPA routing | RSC pages are server-rendered; serving stale HTML shells would fight Next's streaming — cache is a fallback, not the primary path |
| Per-user cache names instead of purge-on-switch | structural isolation beats a purge step someone can forget; shared-device use is common in the PH market |
| Outbox in IndexedDB, not Cache Storage | Blobs + structured metadata + transactional updates; Cache Storage has no query/update semantics |
| Idempotency-Key minted at capture, not at send | the same logical submission must survive N replays across sessions with one identity |
| Domain 4xx = terminal in replay | retrying a `RECEIPT_DUPLICATE` forever burns the 60/day budget and can never succeed |
| 10-item outbox cap | quota safety + a natural offline fraud-velocity bound consistent with server rate limits |
| No offline redemption in v1 | single-use server-signed token is the anti-replay control; weakening it offline reopens threat-model #1 (`../10-architecture/15-security.md`) |
| Business/admin portals excluded from SW | staff decisions (redemption validation, review queues) must never run on stale data |

## Schema deltas proposed

None. The offline layer is deliberately client-side only (IndexedDB + Cache Storage); server-side it leans entirely on existing contracts — `Idempotency-Key` replay (primary) plus server-computed `receipts.sha256` uniqueness for safe outbox drains, `user_devices.fcm_token`/`is_revoked`/`last_seen_at` for the push lifecycle, and `notifications` (`channel='in_app'`) as the universal push fallback.
